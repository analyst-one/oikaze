## Oikaze vs Vanilla CSS Tokens: Managing Design Tokens in Modern Projects {.banner}

Managing design tokens—reusable variables for colors, spacing, typography, etc.—is foundational for scalable CSS and consistent UI. Here we compare **Vanilla CSS tokens** to **Oikaze**.

---

### What Are Vanilla CSS Tokens?

Vanilla CSS tokens are simply custom property definitions written manually in your CSS:

```css
:root {
  --color-brand: #00aaff;
  --space-xs: 4px;
  --font-size-lg: 2rem;
}
```

These variables are usually organized in a root block, copy-pasted between projects, or generated by hand/with simple scripts.

### What Is Oikaze?

Oikaze is a SCSS package that streamlines design token management, allowing you to:

- **Define token maps** in SCSS
- **Auto-generate custom properties** (e.g. CSS variables) from these maps
- **Strongly type-check tokens** at build-time—errors are surfaced if values are missing
- **Compose, transform, and retrieve tokens** with helper functions (e.g., convert color to `rgba`, adjust spacing units, build themes)
- **Forward and organize token sets** with modern SCSS patterns

### Feature-by-Feature Comparison

{.concepts-table}
| Feature | Vanilla CSS Tokens | Oikaze |
| ----------------------------- | ----------------------------------------------- | --------------------------------------------------- |
| **Definition Method** | Manual CSS | SCSS maps & functions |
| **Error Checking** | None (typos/missing tokens are silent) | Compile-time feedback for missing/misused tokens |
| **Reusability/Composition** | Limited—must duplicate for themes/sizes | Supports composition; split tokens for themes/sizes |
| **Unit Manipulation** | Manual (e.g., `calc(var(--space-xs) * 2)`) | Built-in functions: rem/em/alpha |
| **Theme Management** | Requires multiple `:root` blocks, tricky merges | Easily forward/add multiple themes; dynamic mapping |
| **Runtime Performance** | Zero | Zero—output is pure CSS custom properties |
| **Integration** | Direct with CSS | Works with SCSS/Angular/React, etc. |
| **Documentation/Readability** | Simple, but verbose for large projects | Centralized, organized, easy to search and edit |

### Typical Workflow Comparison

#### Vanilla CSS Tokens

- You define tokens in a `:root` block (or several root blocks).
- Reusing tokens in multiple themes or contexts requires manual duplication or third-party scripts.
- No explicit error checking—all errors are silent until runtime.
- Scaling up to hundreds of tokens can be cumbersome.

#### Oikaze

- Tokens are defined as SCSS maps and composed with functions/mixins.
- Custom properties are auto-generated from the maps; themes are built as separate maps/SCSS files.
- Errors surface at build time, preventing mismatches.
- You can scale up token sets, extend themes, and maintain organization effortlessly.

### Code Example Comparison

#### Vanilla CSS

```css
:root {
  --color-primary: #3481f9;
  --space-md: 16px;
}
.button {
  background: var(--color-primary);
  padding: var(--space-md);
}
```

#### Oikaze

```scss
@use 'oikaze' as tokens with (
  $sets: (
    default: (
      color: (
        primary: #3481f9,
      ),
      size: (
        md: 16px,
      ),
    ),
  )
);

:root {
  @include tokens.css-definitions();
}
.button {
  background: tokens.get('color.primary');
  padding: tokens.get('size.md');
}
```
